# ADR-0005: Subscription Filter — 평가 없이 저장만 (당분간)

- 상태: 승인됨
- 날짜: 2026-09-30
- 결정자: 프로젝트 메인테이너

## 배경

통합 플랫폼 도메인 모델 개편(메인테이너 요청, 2026-09-30)에서 Subscription에 Filter 개념을
요청했다 — 예: `status == "DELAYED"` 또는 `delayMinutes > 0`일 때만 전달하도록, 단순히 도달한
모든 이벤트를 매핑하는 것이 아니라 Subscription이 실제로 전달할 이벤트를 좁힐 수 있게. 같은
요청에서 이번 단계에 과도하다면 완전한 규칙 엔진까지 만들지 말고 문서화된 확장 포인트만
남겨두라고 명시했다.

실제 표현식 평가기(파서, 안전한 실행 샌드박스, Canonical Event의 JSON 구조에 맞는 타입 변환
규칙, 이를 작성/검증하는 UI)를 만드는 것은 이번 단계의 다른 모든 작업보다 의미 있게 더 큰
범위다 — 부수적으로 추가할 만한 것이라기보다 그 자체로 하나의 작은 프로젝트에 가깝다.

## 결정

`Subscription.filterExpression`을 nullable text 컬럼으로 추가하고 create/update/response API와
(이후 Stage 3의) 콘솔 UI에 자유 텍스트 필드로 노출한다. **아무것도 이를 평가하지 않는다.**
`IngressService`/`DeliveryService`는 이 컬럼이 생기기 전과 완전히 동일하게, `filterExpression`
내용과 무관하게 활성 상태인 모든 Subscription의 delivery를 큐에 넣고 시도한다.

## 결과

### 긍정적 측면

- 평가 로직이 나중에 만들어질 때를 대비해 도메인 모델과 API 형태가 이미 맞춰져 있다 —
  개념을 추가하기 위한 별도 마이그레이션이 필요 없다.
- 강제가 아직 없더라도 운영자가 의도를 미리 기록할 수 있다("이 Subscription은 지연된
  항공편에만 발동되어야 한다") — 그 자체로 유용한 문서화다.

### 비용과 리스크

- 설정된 것처럼 보이는 filter expression이 실제로는 아무 동작도 하지 않는다 — UI가 이를
  명확히 해야 한다(실제로 활성화된 것처럼 암시하는 체크박스가 아니라, "아직 강제되지
  않음"이라는 눈에 띄는 문구로). UI가 이를 그 이상으로 표현하면 실제 문제가 될 수 있으며,
  Stage 3에서 명시적으로 다뤄야 한다.
- 현재는 어디에서도 표현식 문법을 검증하지 않는다 — 오타가 있어도 지금은 조용히 무해하지만,
  평가 로직이 생기면 이를 드러내야 한다.

## 검토했던 대안

### 지금 최소한의 표현식 평가기를 만든다 (예: `field op literal` 정도의 최소 subset)

이번 단계에서는 기각 — "최소"라 하더라도 안전한 파서, Canonical Event 필드를 읽는 방식(다시
JSONPath? 평탄화된 뷰?), 타입 변환 규칙, delivery 시점에 표현식이 잘못됐을 때의 에러 처리(
delivery를 실패시킬지, 조용히 건너뛸지, 로그만 남기고 전달할지)가 필요하다. 이들 각각은 원래
요청이 이번 단계에 요구하지 않은 실제 설계 결정이며, 잘못 결정하는 것이 아직 기능이 없는
것보다 나쁘다.

### 컬럼 자체를 아예 만들지 않고 미래 설계 메모로만 남긴다

기각 — 메인테이너의 요청은 코드에 흔적이 없는 미래 설계 메모가 아니라, 지금 도메인 모델과
확장 포인트가 존재하기를 구체적으로 요청했다.
