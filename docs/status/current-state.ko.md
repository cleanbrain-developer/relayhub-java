- **ADR-0004** (2026-09-10): Spec 003이 남겨둔 두 gap을 모두 닫았습니다.
  - **Flyway**, 현재 Spring Boot project에서 더 흔한 default이고 이 codebase의 plain-SQL과 잘 맞아서 Liquibase 대신 선택되었습니다. `db/migration/V1__init_schema.sql`은 실제 Hibernate가 생성한 Postgres schema(`pg_dump --schema-only`)를 손으로 정리한 baseline입니다 — 동일한 column/type/nullability/check이며, Hibernate의 hash 대신 의미 있는 constraint 이름을 사용합니다. `ddl-auto`는 이제 `test` profile 밖에서 `validate`입니다; `test` profile(H2)은 `create-drop`을 유지하고 Flyway를 비활성화합니다. migration SQL이 Postgres-specific하기 때문입니다 — `PostgresKafkaIntegrationTest`가 매 `./gradlew test` 실행마다 실제로 `V1__init_schema.sql`을 실행합니다.
  - **Delivery-level idempotency**: `deliveries (event_id, subscription_id)`에 대한 unique constraint와 `DeliveryService.deliver(...)`의 SELECT-before-INSERT check로 인해, Kafka가 재전달한 delivery task(예: worker가 offset을 commit하기 전에 crash한 뒤)는 중복을 만들고 retry loop를 다시 실행하는 대신 기존 `Delivery`를 반환합니다. 드문 진짜 동시성 경우(consumer-group rebalance 중에만 현실적으로 가능)는 uncaught constraint violation으로 전파되도록 의도적으로 두었으며, Kafka의 일반적인 재전달이 재시도하게 됩니다 — 초기의 catch-and-recover-in-the-same-transaction 시도는, Postgres가 하나의 statement가 위반되면 그 transaction을 이후 statement에 대해 사용 불가능하게 만들어 fallback query를 깨뜨린다는 것을 발견한 뒤 rejected되었습니다. `DeliveryDedupTest`로 직접 검증됨(같은 pair에 대해 `deliver()`를 두 번 호출; 하나의 `Delivery`, 하나의 attempt를 assert함).

- Spec 001-003/ADR-0004의 assumption에 대한 열 가지 implementation-driven correction으로, 나중 작업을 위해 알아둘 가치가 있습니다: (1) Spring 6의 `HttpMethod`는 더 이상 단순한 enum이 아니며 JPA의 `@Enumerated`로 매핑할 수 없음 — `common.HttpVerb`; (2) `key`는 H2의 예약어임 — `hibernate.globally_quoted_identifiers: true`; (3) Postgres에서 `@Lob String`은 OID 기반이며 생성한 transaction 밖에서는 다시 읽을 수 없음 — 대신 `@JdbcTypeCode(SqlTypes.LONGVARCHAR)`; (4) `@SpringBootTest`의 context caching은 *동일한* 설정을 가진 test class 간에만 하나의 H2 database를 공유함 — 설정이 다른 class는 별도의 context를 얻으며 DB 이름을 공유해서는 안 됨. 그렇지 않으면 한 context의 `create-drop` teardown이 아직 실행 중인 다른 context의 작업 아래에서 table을 drop시킴; (5) `Delivery.createdAt`은 `save(...)`가 아니라 `saveAndFlush(...)`가 필요했음(insert+update가 하나의 flush로 합쳐져서 `@UpdateTimestamp` generator만 실행되었음); (6) `ddl-auto: update`는 기존 row가 있는 Postgres volume에 `NOT NULL` column을 추가할 수 없음 — 이것이 정확히 ADR-0004의 Flyway migration이 지금 피하는 것임; (7) `@KafkaListener` method가 entity를 load하고 이후 code가 그렇지 않았다면 두 번째 transaction이 되었을 곳에서 lazy association에 접근한다면, 그 method 자체가 `@Transactional`이어야 함; (8) Testcontainers의 `KafkaContainer`는 `confluentinc/cp-kafka` image에서만 동작하며, (`docker-compose.yml`이 사용하는) `apache/kafka`에서는 동작하지 않음 — entrypoint/script가 다름; (9) raw JPQL `@Query`는 Spring Data의 *method-name* parsing에서만 동작하는 derived-query-style 이름(`s.sourceEventId`)이 아니라 실제 association path(`s.sourceEvent.id`)를 사용해야 함; (10) `DataIntegrityViolationException`을 잡아서 *같은* transaction 안에서 다시 query하는 것은 Postgres에서 동작하지 않음 — 위반된 statement는 recovery query 자체를 포함해 그 이후의 모든 것에 대해 transaction을 오염시킴.

- **Demo-profile seed data** (`src/main/java/me/cleanbrain/relayhub/demo/DemoDataSeeder.java`, `application-demo.yml`, 2026-09-10): `demo` Spring profile에 게이트된 `CommandLineRunner`가 매 startup마다 idempotent하게 구체적인 cross-system scenario를 등록합니다. 기본적으로 꺼져 있으며, direct-repository shortcut이 아니라 `SourceService`/`SourceEventService`/`TargetService`/`SubscriptionService`(HTTP API와 동일한 validation path)를 재사용합니다.
  - **Scenario** (*legitimate*한 RelayHub use case — RelayHub가 broker할 필요가 없는 intra-MSA call이 아니라 진짜로 cross-system인 것 — 이면서 동시에 미래의 dashboard에서 시각적으로 흥미로운 것이 무엇일지 광범위한 논의 끝에 정해짐): 시뮬레이션된 항공사 flight-status system, Source `demo-flightstatus`는 `flight-created`(Operation.CREATED, 즉 `POST /ingress/v1/demo-flightstatus/flight-created`)와 `flight-status-updated`(Operation.PATCHED, 즉 `PATCH .../flight-status-updated`) event를 발생시킵니다. 두 개의 external Target이 각각 자신의 mapping template을 통해 구독합니다: `demo-airport-display`(모든 field를 받음: flightNo/status/gate/delayMinutes; 항상 성공)와 `demo-travelapp-vendor`(flightNo+status만 받음 — 실제 third party는 모든 것을 받지 않을 것; `relayhub-demo-systems`가 존재하게 되면 무작위로 실패/timeout하여 DLQ demo에 데이터를 공급함).
  - 실제 Postgres/Kafka에 대해 live로 검증되었으며, field-mapping 자체도 포함됩니다: simulator port의 임시 local echo listener가 각 Target의 template이 (literal `${...}` placeholder가 아니라) 실제로 interpolate된 값으로 올바른 field subset을 렌더링함을 확인했고, CREATE vs PATCH HTTP-verb routing이 동작함을 확인했으며, 도달할 수 없는 Target이 3번의 retry를 정확히 소진하고 `DEAD`(DLQ path)로 이동함을 확인했습니다. Idempotency도 재검증됨(재시작 시 "Seeded ..." 로그 없이 seeder가 다시 실행되며, 중복된 Subscription 없음).

- **`relayhub-demo-systems`** (2026-09-11, [github.com/cleanbrain-developer/relayhub-demo-systems](https://github.com/cleanbrain-developer/relayhub-demo-systems)): flight-status Source와 그 두 Target의 역할을 모두 수행하는 새로운 sibling repo로, Node.js/TypeScript/Express입니다. `setInterval` scheduler가 수동 트리거 없이 5초마다 tick하며, 시뮬레이션된 flight를 생성/진행시켜 이 repo의 Ingress API로 POST/PATCH합니다. `/targets/airport-display`는 항상 성공하고; `/targets/travelapp-vendor`는 즉시 503을 반환하거나 약 6초간 정체된 뒤 504를 반환하기를 무작위로 반복합니다(RelayHub나 script의 로직이 아니라 자체 내부 로직). 실제로 실행 중인 `demo`-profile instance에 대해 end to end로 live 검증됨: 연속적인 tick, 올바르게 mapping된 request를 받는 두 Target, 그리고 — 무인 상태로 — simulator 자체의 flakiness만으로 `DEAD`에 도달한 실제 Delivery(`relayhub_delivery_terminal_total{state="dead"}` 증가함).
- **Docker Compose integration** (2026-09-11): `relayhub-demo-systems`가 multi-stage `Dockerfile`을 얻었고, `docker-compose.yml`은 두 repo가 sibling으로 checkout되어 있다고 가정하는 build context(`../../node/relayhub-demo-systems`)를 가진 opt-in `demo`-profile `demo-systems` service(`docker compose --profile demo up -d demo-systems`)를 얻었습니다. app 자체는 여전히 host에서 실행되므로 container는 `host.docker.internal`을 통해 접근합니다. Live로 검증됨: containerize된 simulator가 build, start되어 host app에 도달했고, Docker 안에서도 Docker 밖에서 실행할 때와 동일하게 실제 Delivery를 `DEAD`로 이끌었습니다.
- **Production deployment** (2026-09-11, `cleanbrain-me-infra`): namespace `cleanbrain-me-relayhub-java`에 네 개의 workload가 있습니다 — `postgres`(StatefulSet+PVC), `kafka`(single-node KRaft, PVC 없음), `api`(이 app), `demo-systems`(`relayhub-demo-systems`, internal-only). 두 개의 별도 source repo가 각각 이 하나의 namespace 안에서 하나의 Deployment를 소유합니다 — 이 infra repo에서는 처음 있는 일입니다 — repo별로 scope된 RBAC(`ci-deployer-relayhub-java`, `ci-deployer-relayhub-demo-systems`)와 함께요. 이 repo를 배포 가능하게 만들기 위해 **어떤 code 변경도 필요하지 않았습니다**: Spring Boot의 environment-variable relaxed binding이 이미 `application.yml`의 하드코딩된 `localhost` default를 override하므로, Kubernetes `ConfigMap`/`Secret`이 container env var만으로 모든 wiring을 처리합니다 — manifest를 작성하기도 전에 build된 image를 env override만으로 `docker run`하여 실제 Postgres/Kafka에 대해 확인했습니다. `relayhub-java.developer.cleanbrain.me`는 완전히 새로운 `developer.cleanbrain.me` DNS subdomain 아래의 첫 hostname입니다(이 repo 자체의 ADR-0002 naming convention에 따름). 전체 manifest, CI build-and-push/deploy job, bootstrap runbook은 `cleanbrain-me-infra`의 README "relayhub-java" section에 있습니다 — 그 repo가 infra 세부사항의 source of truth이며, 여기서 중복하지 않습니다.
  - rollout 도중 두 가지 실제 production issue가 발생하여 수정되었습니다(둘 다 infra repo 자체의 manifest 주석과 commit history에 문서화됨): (1) 첫 배포에서 shared Gateway의 TLS listener를 놓쳤음(그 repo의 README가 이미 `kioti-crm-discount`에 대해 flag했던 것과 같은 종류의 실수 — `HTTPRoute`는 healthy하고 DNS는 resolve되었지만, 실제 인증서 대신 `TRAEFIK DEFAULT CERT`가 제공됨); (2) Kafka의 `advertised.listeners`가 기본적으로 `localhost:9092`였는데, 이는 local `docker-compose`에서만 우연히 동작했습니다(app이 host에서 실행되고 port가 publish되었기 때문). in-cluster 환경에서는 이로 인해 모든 Outbox→Kafka publish가 영원히 조용하게 실패했습니다. 이를 고치려면 KRaft bootstrap env var 전체 집합이 함께 필요했습니다(`KAFKA_ADVERTISED_LISTENERS`만으로는 broker가 "missing `zookeeper.connect`"로 crash-loop함) — 전체 집합과 각각이 왜 필요한지는 `cleanbrain-me-infra`의 `kubernetes/apps/relayhub-java/kafka/deployment.yaml`을 참고하세요.
  - 실제 evidence로 live 검증됨: `openssl s_client`가 진짜 Let's Encrypt certificate를 보여줌; `curl .../actuator/health`가 `db`가 connected 상태로 `UP`을 반환함; 그리고 — 이 전체 demo-observability arc의 실제 성과 — `relayhub_delivery_terminal_total{state="dead"}`가 production에서 실제로 증가하고 있으며, 이는 수동 조작 없이 설계된 그대로 전체 무인 loop(relayhub-demo-systems 트래픽 → Ingress → Outbox → Kafka → DeliveryWorker → retry → 실제 DLQ entry)가 동작함을 증명합니다.

  - `specs/001-push-event-delivery/verification.md`는 여전히 (이제 삭제되어 `AGENTS.md`로 merge된) `.ai/constitution/agent-behavior.md`를 두 곳에서 참조하고 있습니다. 아래의 향후 Spec Kit migration을 기다리며 `specs/001`-`006` tree를 그대로 두는 것과 일관되게, 이것은 수정하지 않고 그대로 두었습니다 — 조용히 깨진 상태로 두지 않고 여기에 기록해 둡니다.

## Open decisions

- `relayhub-node`(또는 다른 언어) sibling repository가 실제로 만들어질지, 만들어진다면 언제일지.
- `Subscription.retryPolicy`는 여전히 parse되지 않은 free-text field로 남아 있습니다; 그 field가 무엇을 말하든 상관없이 고정된 policy(3회 시도, 200ms/400ms backoff)가 모든 Subscription에 적용됩니다(ADR-0003 참고).
- Outbox row cleanup/archival은 다루어지지 않았습니다(Spec 003 "Deliberately out of scope") — local MVP에서는 괜찮지만, 장기적으로 지속되는 것이 있기 전에 재검토합니다.
- Spec 006의 "Deliberately out of scope" 목록은 그대로 유지됩니다: Subscription의 mapping이 실제로 등록된 field를 사용하는지 검증하는 것은 없으며, schema-inference auto-population도 없습니다 — 진짜 필요성이 나타나지 않는 한 registry는 hard constraint가 아니라 documentation/autocomplete aid로 남습니다.
- 위의 console-iteration 작업 동안 이 파일 자체가 하루, 23개 commit만큼 오래된 상태로 남아 있었습니다. 개별 maintainer 후속 요청이 잠시 멈출 만한 session boundary처럼 느껴지지 않았기 때문입니다 — 이것이 `agent-dev-starter` 자체에 반영되었습니다(2026-09-12: `using-the-starter.md`의 update trigger는 이제 "session boundary"가 아니라 "출시되고 검증된 변경"입니다; 같은 pass에서 발견된 `specs/006-field-registry/spec.md` 자체의 오래된 "Design only" Status line이, 이제 `agent-context-model.md`가 feature별 spec status도 working context로 명명하게 만든 계기입니다). 자연스러운 멈춤 지점처럼 느껴지는 순간뿐만 아니라, 앞으로의 어떤 장기 iterative session에서도 이 파일이 실제로 current한지 주기적으로 확인할 가치가 있습니다.

## Known constraints

- Kafka topic partitioning은 single-partition입니다; worker가 두 개 이상의 instance로 실행되는 것은 test되지 않았습니다.
- Delivery-task dedup의 진짜 동시성 race path(consumer-group-rebalance window에서만 발생)는 automated test로 커버되지 않습니다 — 추가적인 복잡성을 더하는 대신 documented gap으로 받아들여졌습니다(ADR-0004 "Costs and risks" 참고).
- Prometheus의 scrape target(`observability/prometheus/prometheus.yml`의 `host.docker.internal:8080`)은 Docker Desktop을 가정합니다; native Linux Docker는 다른 접근이 필요할 것입니다(예: `docker-compose.yml`의 `extra_hosts`를 통해 `--add-host`가 이미 설정되어 있지만, Docker Desktop 밖에서는 검증되지 않았습니다).
- Alerting/SLO/log aggregation이 없습니다 — personal project를 위해 의도적으로 범위 밖입니다(`specs/004-observability/spec.md` 참고).
- 실제 GitHub Spec Kit CLI(`specify-cli==1.0.8`, `PROJECT.yaml`의 `standards.spec_kit.pinned_version`에 pin됨, `agent-dev-starter`의 `ADR-0010` 참고)는 이 repository에 실제로 설치되어 있지 않습니다 — 2026-09-20 ADS V2 migration을 수행한 session에는 `specify init`을 실행할 작동하는 Python/`uv`/`pip` toolchain이 없었습니다. `.specify/memory/constitution.md`는 존재합니다(이 repo 자체의 이전 내용으로부터 손으로 작성됨) 그러나 `.specify/`의 나머지 Spec-Kit-managed 파일들(template, script, `.claude/skills/speckit-*/SKILL.md`)은 존재하지 않습니다.
- `specs/001-push-event-delivery/`부터 `specs/006-field-registry/`까지는 이 project 고유의 pre-Spec-Kit feature tree이며, Spec Kit 자체의 `specs/<NNN-feature>/` 구조로 migrate되지 않았습니다 — 이 변환에는 위 제약사항에서 설명한 실제 `specify` CLI가 필요합니다. `specs/001-push-event-delivery/verification.md`도 (이제 `AGENTS.md`로 merge되어 삭제된) `.ai/constitution/agent-behavior.md`를 두 곳에서 여전히 참조하고 있으며, 그 migration이 이루어지기 전까지는 수정하지 않은 채로 남아 있습니다.
